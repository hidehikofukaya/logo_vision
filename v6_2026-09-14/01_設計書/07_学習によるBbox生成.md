# 07. 学習による Bbox 生成

- 開始: 2026-09-12
- 状態: **データセット再生成中 / 学習は未完（v1 は破棄）**
- 目標: **正解 Bbox を 100% 覆う。そのうえで面積を 100% に近づける**

---

## 1. なぜ学習に進んだか

手作りの特徴を 5 つ試し、**必要条件としての排除率が 85% で頭打ち**になった
（`docs/06_` §12〜13、§17）。

| 特徴 | 排除率（正解 100% 残存） |
|---|---|
| エッジ密度 | 84.2% |
| 学習済み conv1 の pos−neg | 79.1% |
| 方向エントロピー / 最大連結成分 / 説明率 | 分離せず |
| （AND 併用） | 85.5% |

**「構造がある」は測れるが、「マークの構造がある」は手作りでは測れない。**

さらに吸音材（`docs/05_` §11）を入れたことで、これは決定的になった。

> 吸音材の**背景の勾配 95 分位 197.5** は、ガラスの**刻印** 142.1 より強い。
> 「輪郭が強い所を探す」方針は原理的に効かない。
> 効くのは「くぼみの陰影」と「繊維が潰れて平滑になること」で、
> **後者は勾配方向の量子化（LINE-2D）では拾えない量。**

## 2. few-shot 要件をどう守るか

**図面 1 枚/品番**は絶対条件。学習を入れても壊さないために、2 つを課す。

### 2.1 品番は重みに入れない

網が判定するのは「**刻印らしい構造か**」だけ。どの品番かは見ない。
品番テンプレートは実行時の入力のまま。

### 2.2 受容野を 25px に縛る

`docs/06_` §19 の実測で、受容野を広げるほど未知系統への汎化が落ちた。

| 受容野 | logo | letter | code |
|---|---|---|---|
| 16px | 94.6% | 89.2% | 93.0% |
| 24px | **100.0%** | 90.9% | 94.7% |
| 32px | 100.0% | 98.2% | **46.2%** |
| 48px | 88.9% | **22.5%** | — |

この幅では**マーク全体が絶対に見えない**ので、形を記憶できない。
記憶できないことを、アーキテクチャで保証する。

## 3. データセット（`tools/make_dataset.py`）

### 3.1 組み合わせ

| 軸 | 内容 |
|---|---|
| 材質 | ガラス / 板金 / **吸音材** |
| 部品の構造 | 板金 normal / dense / ribbed、板寸 3 種 |
| テンプレート | 手続き生成ロゴ + 語彙 12/23/10 種 + 囲みマーク 4 形 |
| 背景 | 工場 HDRI。**train/val は 0-2、gen は 3-5**（未見環境として取り置く） |
| **画角** | **網羅的な格子**: 傾き 5 x 方位 5 x ロール 3 = **63 視点** |
| 距離 | 視点ごとに巡回（刻印が画面幅の 14 / 26 / 42%） |
| 手ブレ・ピンぼけ | **レンダ後の ISP で**強弱を振る（下記） |

**59 シーン x 63 視点 = 3,717 枚。**`--mult 5` で 295 シーン / 18,585 枚。

### 3.2 画角を格子にした理由

無作為抽出だと、同じ枚数でも角度に偏りが残る。
**学習と評価を角度で切り分けたい**ので格子で回す。
傾き 0 度では方位が退化するので 1 通りだけ置く（→ 21 方向 x 3 ロール = 63）。

### 3.3 手ブレとピンぼけは学習時に掛ける

どちらも**光学段**なので、露出・ノイズより前に入れる。
レンダを作り直さずに強弱を振れるので、**学習時の増強**として扱う。

```
ピンぼけ(円盤カーネル) → 手ブレ(線状) → 露出(中央重点) → ノイズ(センサ) → トーン → 8bit
```

- ピンぼけは**ガウシアンではなく円盤**。実際の錯乱円は円盤で、
  鏡面ハイライトが「にじむ」のではなく「円に広がる」
- 強弱: ブレ 0/1.0/2.0/3.5/5.5px、ボケ 0/0.8/1.6/3.0px（0 を厚めに）

### 3.4 分割

| 分割 | シーン | 内容 |
|---|---|---|
| train | 30 + 9(felt) | 手続き生成ロゴのみ、HDRI 0-2 |
| val | 6 + 2 | 同じ分布・別シード。**較正はここだけで行う** |
| **gen** | 9 + 3 | **本物の Honda ロゴ + 未見 HDRI 3-5。**汎化検証用に取り置き |

gen は「学習後に似て非なる刻印が出てきたら」を再現する。**最後に 1 度だけ測る。**

## 4. 【重要】遮蔽の正解バグ（ユーザー指摘、2026-09-12）

> 謎の板で部品が遮られていることがあるが、これを学習に入れると
> **何もない所で予測させるモデルになる**のではないか

**指摘どおりのバグだった。**

| | 内容 |
|---|---|
| 原因1 | `add_occluder()` が部品の**真上 0.6〜1.9 板幅**に板を置く。カメラは 85〜320mm から見るので**間に入る** |
| 原因2 | `project_boxes()` の `visible` が**画面内かどうかだけ**で、遮蔽を見ていない |
| 被害 | **マークの 14.7% が板の裏に隠れたまま正解箱付き** |

**対処:**

1. 遮蔽物の役目は「光を遮る」こと。カメラ設置後に**視線から横へ退かす**
2. `mark_occlusion()` を追加。カメラから各マークへ 3x3 の光線を飛ばし、
   **手前で何かに当たるか**を実測。`unoccluded < 0.6` なら `visible=false`
3. これは板の曲げ・ビードによる**自己遮蔽**も拾う（修正後に残る 7.1% がそれ）

**副次的な教訓:** Blender は Python 例外でも**終了コード 0 を返すことがある**。
`make_dataset.run()` は戻り値ではなく**成果物（index.json の件数）で成否を判定**するよう変更した。
これを直すまで、壊れたまま「OK」が 45 行並んでいた。

## 5. 網（`tools/markseg.py`）

```
入力 2 面（輝度 / 局所コントラスト）
   │
   ├─ s1  3x3         受容野  3, stride 1
   ├─ s2  3x3 /2 + 3x3  受容野  9, stride 2
   ├─ s4  3x3 /2 + 3x3  受容野 21, stride 4
   │
   └─ 融合（stride 2 へ戻して浅い枝と足す）受容野 25
        ├─ seg  1x1        マークの構造か（受容野 25px のまま）
        └─ box  拡張3x3 x2  四辺までの距離（受容野 ~117px）
```

**0.23M パラメータ。**受容野は実測で 25px（`demo()` が assert で検証する）。

- **入力の 2 面目は局所コントラスト**（自分 − 25px 窓の平均）。
  刻印は「周りに対する局所的なずれ」なので、素の輝度より直接的な量。
  照明ムラや露出の違いにも強い
- **出力は stride 2。**正解箱の短辺は 19% が 20px 未満（中央値 36px）で、
  stride 4 だと量子化誤差が支配し余白を詰められない

### 5.1 箱の取り出しは 3 通り

| 経路 | まとめ方 | 範囲 | 性質 |
|---|---|---|---|
| `group` | 連結成分 | seg 画素 | **学習ゼロ。**原理的に安全だが行が隣接すると融合する |
| `ltrb` | 回帰 + NMS | 回帰値 | 分離はよいが受容野が広く、未知の形で外しやすい |
| **`hybrid`** | **ltrb で束ねる** | **seg 画素** | 役割を分ける。範囲は受容野 25px の頭だけで決まる |

範囲は stride の**外側**へ丸める。内側へ丸めると被覆漏れの原因になる。

## 6. 被覆率 100% をどう出すか

2 段。

1. **非対称な箱の損失。**箱を縮める誤りを広げる誤りより 3 倍重く罰し、
   系統的な偏りを外向きに倒す
2. **val でマージンを較正**（`tools/calibrate_boxes.py`）。
   `a * 箱の長辺 + b 画素` の (閾値, a, b) を格子探索し、
   被覆率が目標に届く中で**面積比が最小**の組を選ぶ。split conformal の考え方

量子化誤差は**絶対値**で効くので `b` が要り、見落とした端は箱の大きさに比例するので `a` も要る。

## 8. 評価軸の転換 — 「個別の刻印」が主指標（2026-09-12）

**ユーザー指示:**
> 最終 Bbox で損失評価というよりは、個別の刻印が正しく認識できているかが大事。
> 最終 Bbox は決定論的に出すことも最悪可能。

そのとおりで、最終 Bbox は「検出 + 図面の配置」から決定論的に投影できる。
**測るべきは 1 個 1 個のマークの認識の質。**

### 8.1 新しい指標（`tools/eval_marks.py`）

| 記号 | 意味 |
|---|---|
| **R** | 検出率（中心が許容内・大きさが合う・細長ければ向きも合う） |
| **E** | 中心のずれ（マーク長辺に対する比） |
| **S** | 大きさの食い違い（\|log 比\|） |
| **A** | 向きのずれ（度） |
| **K2w** | **離れた 2 個が取れたコマの割合** |

**K2w が主指標。**変換を決めるには 2 点あればよいが、
近い 2 点だと誤差が増幅する（§9 の実測: 近い 2 点で 95 分位 170px、
離れた 2 点で 4.9px）。だから「2 個取れたか」ではなく
「**離れた 2 個が取れたか**」を数える。

最終 Bbox の被覆率も出すが、**K2w の結果**であって主指標ではない。

### 8.2 学習の選び方も変えた

チェックポイントの選択は **`K2w + 0.20 x R`**。

それ以前は「余白 +20% での被覆率」で選んでいて、
**面積 16 倍のゆるいモデルを「最良」と判定していた**（実害あり。
16 エポック回して残ったのが ep2 の重みだった）。

## 9. 検出 1〜2 個から全マークを投影する（`tools/propagate.py`）

図面 1 枚には全マークの相対配置が載っている。だから確実に取れたマークだけで
図面→写真の変換を決め、**残りは投影で出せる**。
被覆率が「検出率」ではなく「**変換の精度**」で決まるので、100% 被覆に有利。

対応（どの検出がどのマークか）は分からないので、**総当たりで辻褄が合うものを採る**
（RANSAC の考え方。マークは高々 7 個なので総当たりで足りる）。

### 9.1 条件数 —— 「どの 2 個か」で結果が全く違う

検出箱に std 2px の雑音を載せた 200 回試行:

| 取れたマーク | 条件数 | 誤差中央 | 95 分位 |
|---|---|---|---|
| 近い 2 個 | 4.4 | 12.7px | **170.9px** |
| **離れた 2 個** | 1.0 | 2.9px | **4.9px** |
| 4 個すべて | 1.0 | 2.8px | 5.0px |

**条件数 = 図面全体の広がり ÷ 使った点の広がり** が、そのまま誤差の増幅率になる。
マージンをこれに比例させれば、**悪条件のコマだけ余白を広げ、良条件のコマは締めたまま**にできる。

## 10. 方向付き矩形（OBB）— 指標が正しくなった

**ユーザー指摘:**
> 刻印の各要素の Bbox は縦横の軸の矩形ではなく、方向付きの矩形で生成できないか。
> そのほうが損失はより正しく計算できるはず。

### 10.1 軸平行がどれだけ歪めていたか（実測）

| 種別 | 縦横比 | **AABB / OBB 面積** | 95 分位 |
|---|---|---|---|
| **text** | 7.4 | **3.56 倍** | 5.46 倍 |
| **code** | 4.4 | **2.61 倍** | 4.00 倍 |
| circled | 1.0 | 1.72 倍 | 1.94 倍 |
| logo | 1.2 | 1.73 倍 | 1.98 倍 |
| **全体** | | **2.39 倍** | **4.54 倍** |

**面積の 2/3 以上が「回転由来の水増し」。**
それまで報告していた「面積 ○ 倍」の相当部分がこれだった。
損失も、回転誤差と位置誤差を混同していた。

### 10.2 実装（`tools/obb.py`）とコスト

表現は `(cx, cy, w, h, deg)`。**必ず w >= h に正規化**し、
deg は**長辺の向き**を [-90, 90) で持つ（矩形は 180 度で同一なのでこれで一意）。

| 箇所 | 実装 | 速度 |
|---|---|---|
| 正解 | H で四隅を射影 -> `cv2.minAreaRect` | **ゼロ**（レンダのやり直し不要） |
| **`group` 経路** | 連結成分の**画素に `minAreaRect`** | **ほぼゼロ** |
| 学習ヘッド（未実装） | ltrb 4ch -> (cx,cy,w,h,sin2θ,cos2θ) 6ch | +0.5% |
| 損失（未実装） | 回転 IoU は微分不可 -> **ガウス表現（KLD/GWD）** | ほぼゼロ |
| NMS | 回転 IoU は軸平行の 5〜10 倍 | **ここだけが実コスト** |

**`group` 経路なら OBB 化のコストは実質ゼロ。**連結成分で束ねるので回転 NMS も要らない。
いま主指標（中心精度）で `group` が `hybrid` を上回っているので、そこを主にする。

### 10.3 OBB にして見えたこと

**中心精度は実は良かった。**

| | AABB 評価 | **OBB 評価** |
|---|---|---|
| 中心のずれ E | 0.089 | **0.047** |
| 大きさの食い違い S | 0.208 | **0.083** |

**AABB が測定誤差を作っていた。**中心はマーク長辺の 4.7% に収まっていた。

**向きのずれは二極化する。**中央 6.2 度 / 95 分位 63.9 度。
細長いマークは向きが決まるが、正方形に近いマークでは定まらない。

## 11. 【重要】OBB なら**検出 1 個**で変換が決まる

方向付き矩形 1 個から

```
中心     -> 位置
長辺の比 -> 倍率
長辺の向き -> 回転
```

がすべて取れる。軸平行では回転が取れず 2 個必要だった。

### 11.1 実測

| 検出 | 条件数 | 最大誤差 |
|---|---|---|
| **1 個（細長 34x5、縦横比 6.8）** | **1.5** | **0.00px** |
| 1 個（ロゴ 18x16、縦横比 1.1） | 40.0 | 110.65px |
| 1 個（正方 7x7、縦横比 1.0） | 40.0 | 180.48px |
| 2 個 | 1.5 | 0.00px |

**細長いマークが 1 個取れれば、それだけで全マークの Bbox が完全に復元できる。**

正方形に近いマークでは長辺の向きが定まらないので、
条件数を `6 / (縦横比 - 1)` として自動的に「当てにならない」と判定させる。
誤差 110〜180px がまさにそれで、**マージンをこの条件数に比例させれば被覆は保てる**。

### 11.2 これが意味すること

| | AABB | **OBB** |
|---|---|---|
| 必要な検出数 | 離れた 2 個 | **細長いもの 1 個** |
| 最も検出率が低い `code`（縦横比 4.4） | 分離が難しい | **1 個取れれば十分。しかも向き推定に最適** |

**最も難しかった種別が、最も変換推定に貢献する。**縦横比が大きいほど向きが安定するため。

180 度の曖昧さ（矩形は裏返しても同じ）は両方を試し、他マークとの辻褄で決める。

## 14. 端の文字が読めないときに何が起きるか（実測、2026-09-12）

**ユーザー指摘:**
> 端の文字が精度上読み取れなかった場合に、それでも正しい Bbox が出せなければいけない。
> 純粋な CNN では限界ではないか。ViT に活路はあるか。

### 14.1 壊れ方は「Bbox が切れる」ではない

最終 Bbox は検出の和集合ではなく**図面の投影**なので、切れることはない。
実際に壊れるのは別の 2 つ。

1. **倍率が狂う。**長辺から倍率を取ると、60% しか見えなければ倍率が 40% 小さく出る
   → **短辺（行の高さ）から取るよう修正。**端が欠けても行の高さは変わらない
2. **中心が行方向へずれる。**これが本命

誤差を方向別に分解した（片端 60% 欠け、150 回）:

```
行方向のずれ    中央 47.6px
垂直方向のずれ  中央  0.0px   ← 完全に無傷
```

**行方向の絶対位置だけが失われる。**垂直位置・倍率・回転はすべて無傷。

### 14.2 これは CNN の限界ではない

情報が画像に存在しないので、**どんなアーキテクチャでも取れない。**
受容野を広げても、ViT にしても、無い情報は出てこない。

試して効かなかった手も記録しておく。

| 試した手 | 結果 |
|---|---|
| 端を合わせる仮説を列挙して辻褄で選ぶ | **効かない。**複数行がバラバラの側で欠けると選ぶ基準が無い |
| 中心を等方に測る | 壊れている軸（行方向）に引きずられる |
| 中心を異方に測る（行方向 0.25 倍） | 改善するが、残差 32px（行長の 13%）が残る |

### 14.3 ViT の評価

**画像パッチの ViT はこの問題を解かない。**

- 行方向の位置情報が画像に無いので、受容野を広げても取れない
- `docs/06_` §19 の実測（受容野 32px で汎化 46%、48px で 22.5%）と正面から衝突する

**活路は 2 つあるが、いずれも画像パッチの ViT ではない。**

| 案 | 内容 | 判断 |
|---|---|---|
| 検出集合への attention | 数十個の検出（位置・寸法・向き）に小さな Transformer | RANSAC が 7 個までなら厳密なので、文字単位に降りたとき限定 |
| **行の内容を読む** | `>PET<` と `>ABS<` を読み分ければ一意に決まる | **本質的な解。**ただし図面が候補文字列を持つので、認識でなく**数個との照合**で済む |

### 14.4 ロゴに依存しないこと（指示）

> ロゴ優先は再検討が必要。文字だけの刻印の場合がある。

そのとおりで、板金は大文字 + コード行、吸音材はコード行だけの図面がある。
効いているのは「ロゴだから」ではなく「**図面の中で他と紛れないから**」。

`uniqueness(marks)` として一般化した。検出から測れる (短辺, 長辺, 向き) で、
最も似ている他マークとの隔たりを見る。**図面だけから計算できるので実行時コストはゼロ。**

```
ガラス : logo 1.00  code 0.08  code 0.08  code 0.18
板金   : letter 1.00  code 0.08  code 0.08  code 0.18   ← 大文字が同じ役割
吸音材 : code 0.08  code 0.08  code 0.18                 ← 紛れないマークが無い
```

条件数に `1/uniqueness` を掛ける。ロゴという語は設計から外れた。

### 14.5 いまの到達点（余白を辺ごとに正した後）

| 図面 | 検出 | 余白 12%+8px での被覆 | 面積比 |
|---|---|---|---|
| ロゴ+行3 | 完全 | **100%** | 2.22 |
| 大文字+行3（ロゴなし） | 完全 | **100%** | 2.20 |
| 行3のみ（吸音材） | 完全 | 81% | 2.05 |
| （参考）片端 70% 欠け | | 1〜28% | 2.3 |

**検出が完全なら、ロゴが無くても 100% 被覆・面積 2.2 倍。**要件（面積比 2.0）とほぼ同水準。

### 14.6 【重要】マージンは辺ごとに比例させる

長辺に対する比を**全辺に**足していた。細長いマークで短辺が壊滅的に膨らみ、
36x5mm の行に「長辺の 10%」を足すと**面積が 3.5 倍**になっていた。
辺ごとに比例させて 1.5 倍に。**それまでの面積比の報告はこの分だけ悪く出ていた。**

### 14.7 ここで止める理由

**「端が欠ける」がどれくらい起きるのかを、まだ測っていない。**

- 欠けはシミュレーションで作ったもので、実データでの発生率は不明
- 1024px 化でマーク長辺が中央 200px になり、端の文字も十分な画素を持つ
- 学習済みモデルが無いので測れない

**順序は「学習 → 欠けの実測 → 必要なら行内容の照合」。**
起きるかどうか分からない問題に先回りしない。

## 16. 【訂正】「膨張は不要」は誤りだった

以前「連結成分の膨張は不要（gap=0 で 1 対 1 率 93%）」と報告したが、**指標が誤っていた。**

そのときの「1 対 1 率」は**成分が GT 中心を 1 個含むか**しか見ておらず、
**1 文字だけの成分も「1 対 1」と数えていた。**成分がマークを覆っているかを見ていない。

正しい照合基準（中心・寸法・向きが合うか = `eval_marks.match_marks`）で測り直した結果:

| 設定 | 成分数 | **R（正解 seg での上限）** | code の R |
|---|---|---|---|
| 膨張なし | 1,433 | 51.8% | 45.4% |
| **等方 gap=1** | 523 | **71.1%** | **81.1%** |
| 等方 gap=2 | 339 | 56.2% | 76.1% |
| 等方 gap=3 | 250 | 44.1% | 64.3% |
| 方向性 長3短1（学習時の既定） | 362 | 60.1% | 79.4% |

**既定を等方 gap=1 に変更。**学習時は方向性膨張（上限 60.1%）で評価していた。

方向性の膨張（行方向にだけ伸ばす）は理屈は正しいが、行が融合した状態では
向きの推定が当てにならず、等方 gap=1 に劣った。

## 17. 【重要】検査ツールが機能していなかった

`verify_dataset` の A6（画角）は **`rec["frac"]` という記録値を読んでいた。**
レンダラのバグはレンダラの出力では検出できない。

実測したところ、記録と実態が食い違っていた。

| | 記録 | 実測 |
|---|---|---|
| 画角 frac | 0.22〜0.94（中央 0.54） | **0.10〜0.70（中央 0.33）** |
| 可視マーク 0 個のコマ | 検査していない | **11.1%** |

**約 700 コマが「マークが 1 つも見えない」画像**だった。学習では正例ゼロになる。

### 17.1 原因

| frac 帯 | 可視 0 率 |
|---|---|
| 0.0-0.3 | 1.8% |
| 0.5-0.7 | **17.1%** |

**寄るほど画面外に出る。**遮蔽物の有無とは無関係（遮蔽なしでも 9.1%）。

`span` を「刻印ブロックの長い方の辺」で取っていたため、
**ロール（0/120/240 度）で回すと対角方向がはみ出す**。
傾き 44 度では短縮も効き、実測は記録の 0.77 倍になっていた。

### 17.2 対処

| 箇所 | 修正 |
|---|---|
| レンダ `span` | **外接円の直径**（`hypot(w, h)`）。どう回してもはみ出さない |
| レンダ 画角 | **cos(傾き) で補正**。短縮を見込む |
| 検査 A6 | **記録を読まず、正解 H で四隅を射影して実測** |
| 検査 A8（新設） | **可視マーク 0 個のコマを失格に** |

**教訓: 検査は独立した経路で測らなければ意味がない。**

## 18. 【失敗の記録】変更を一度に 3 つ入れた（2026-09-13）

材質の偏り（ガラス p=0.55 / 板金・吸音材 p=0.24）への対処として、
**3 つの変更を一度に投入した。学習が壊れた。**

| # | 変更 | 結果 |
|---|---|---|
| 1 | 損失をコマごとに正規化 | **これが原因だった** |
| 2 | 材質を均等にサンプリング | 未検証のまま |
| 3 | 入力に局所のざらつき面（2 面 -> 3 面） | 未検証のまま |

### 18.1 何が起きたか

| | ep1 の seg 損失 | ep1 の R | ep3 の R |
|---|---|---|---|
| 元の設定（成功） | 0.989 | 1.2% | **21.1%** |
| 3 つ同時 | 2.159 | 0.0% | 0.0% |
| 正規化を戻した | 1.125 | 6.0% | 0.0% |

### 18.2 なぜコマごと正規化が壊したか

意図は「正例の学習を材質間で釣り合わせる」ことだった。実際には逆に働いた。

```
コマごと正規化 = そのコマの損失合計 / そのコマの正例数
```

正例が 50 個しかないコマでは、**負例 49,000 画素分の損失まで 50 で割られる**。
つまり**負例側の勾配が 1,000 倍に増幅**される。網は「全部背景」へ押される。

さらに悪いことに、**正例が 0 のコマ（実測 11.1%）**では `clamp_min(1.0)` で
1 で割られ、通常コマの 200 倍の重みになっていた。

**正規化はバッチ全体の正例数で行う（RetinaNet と同じ）のが正しい。**
材質間の釣り合いは**サンプリング側**で取るべきだった。

### 18.3 教訓

**学習 1 回に 2 時間かかる状況で、変更を一度に 3 つ入れたのが誤り。**
効いているものと壊しているものを切り分けられなくなった。

正しい進め方は、**変更ごとに短い学習（3〜4 エポック）で切り分ける**こと。
成功した学習は ep3 で R 21% に達していたので、3〜4 エポックあれば判定できる。

| # | 材質均等 | ざらつき面 | R@ep3 |
|---|---|---|---|
| A | なし | なし | **21.1%（既知）** |
| B | あり | なし | 検証中 |
| C | なし | あり | 検証中 |
| D | あり | あり | 0.0% |

`--balance` / `--tex` のフラグを用意して切り分けられるようにした。

## 19. レンダ前に幾何で検算する（2026-09-13、ユーザー提案）

「刻印が部品に隠れて読めないなら、部品幾何を計算して事前に検算できないか」
「刻印が読める部品アングルとカメラアングルを自動で決められるとなお良い」
という指示。**レンダは 1 枚 2 秒かかるので、撮る前に決めた方がよい。**

### 19.1 2 つのツール

| ツール | 何を見るか | 出力 |
|---|---|---|
| `tools/check_geometry.py` | 刻印が**地形に埋もれていないか** | 深さ / 起伏、面の傾き |
| `tools/view_sampler.py` | その視点から**稜線に隠れないか** | 読める (傾き, 方位) の一覧 |

どちらも高さマップと刻印マスクだけで決まる。Blender も cv2 も要らない
（`view_sampler` は cv2 を使うが、**Blender の外**で走る）。
`prep_scene.py` が両方を呼び、結果を npz に `good_views / geo_ratio / geo_slope`
として書く。`render_scene.py` はそれを読んで視点を選ぶ（`--all-views` で無効化）。

### 19.2 「深さ / 起伏」の定義は 2 回直した

**(a) マークごとに見る。**刻印域をまとめて 1 領域とすると、板全体の緩い曲率まで
起伏に数える。実測: 板金でまとめると 0.14（NG）、マークごとだと大半が 2〜15。

**(b) 最良近似平面を引いてから測る。**一様な傾きは刻印を埋めない。陰影が全体に
等しく変わるだけで、見かけの角度が変わる（それは 45 度制約が扱う）。刻印を
消すのは**稜線やコブ＝曲率**。実測: 板金の行の下は 4.7mm で 0.77mm の一様な坂
（約 9 度）だった。平面を引くと残差 0.02mm。

**(c) 凹凸が無いマークは「印刷」として除外する。**ガラスの白セラミック焼き付けは
アルベドで見えるので、地形に埋もれるという概念が無い（深さ 0.000mm → 判定 OK）。

### 19.3 吸音材: 版は面で当たる

刻印を**文字の形だけ**平していたため、文字間・行間に繊維の起伏が残り、
1 マークの中で地形が刻印を上回っていた（合格率 71%、深さ/起伏 の中央 1.31）。

実物の版（ダイ）は**面で当たる**。マークの外接矩形 +1.5mm を版の footprint と
して、その中の繊維を潰すようにした。**版の輪郭そのものは段差にしない**
（矩形の外形が出ると、検出器がマーク本体でなく版の枠を当てにできる。
不当に易しくなる）。→ 6 シーン連続で合格、深さ/起伏 1.47〜6.89。

## 20. 画角を「投影で」合わせる（2026-09-13）

指示は「刻印全体の Bbox が画面の 20〜70%」。これを mm の外接円から逆算していたが、
**ロールと傾きの分だけ実際の写り方がずれる。**

| 症状 | 実測 |
|---|---|
| 対角で決めると小さく写る | 要求 0.65 → 画面上 0.42 |
| 要求 0.26 で下限割れ | 画面上 0.17 |
| デジタルズームが 1 倍で止まる | 要求 0.65 → 画面上 0.90（寄りすぎ） |

**対処**: カメラを置いて H を作り、`block_frac(H, boxes)` で画面占有率を測り、
レンズを `frac / 実測` 倍する。レンズの端（1〜10 倍）に当たったら距離で合わせる。
3% 以内に入るまで最大 5 回。**レンダしないので安い。**
結果は 18 コマすべて要求どおり（0.20〜0.69）。測定値は `index.json` の
`frac_img` に残す（`frac` は要求値でなく span 由来の派生値なので、
これを見ないと指示を満たしているか確認できない）。

副作用として、**近すぎて可視 0 になっていたコマが直った**
（13mm レンズ 34mm 距離 → 49mm。可視 0/3 → 3/3）。

## 23. 検査ツール側の定義ずれと、白飛びの見落とし（2026-09-13）

作り直したデータに `verify_dataset` を掛けて出た 3 件。**2 件は検査側の誤り**だった。

### 23.1 A6「画角」— 検査とレンダで定義が違った

レンダ側は `block_frac` ＝ **全マーク**の投影の「幅/画面幅 と 高さ/画面高さ の**大きい方**」。
検査側は **可視マークだけ**の「幅/画面幅」。この 2 つを比べていたので、
レンダ 0.20〜0.69 に対し検査 0.03〜0.68 と出て、吸音材の 19 件が「画角違反」に見えた。

- 可視だけで測ると、**遮蔽で小さく出たものが画角違反に化ける**
- 幅だけで測ると、**縦長のブロック（吸音材は 1〜3 行で縦に積む）が過小に出る**

定義を揃えたら **0.21〜0.69**。データは正しく、**検査が間違っていた。**

### 23.2 A5「枚数不足」— 視点の事前選別で減るのが正しい

`view_sampler` が「読めない視点は撮らない」ので、63 コマちょうどにはならない
（吸音材 2 シーンが 54 コマ）。**減ること自体が意図した挙動。**
半分を切ったときだけ落とすようにし、減ったシーン数は情報として出す。

### 23.3 白飛びしたマークに正解箱が付いていた（**実データの誤り**）

遮蔽は光線で測っていたが、**露出で情報が落ちる場合を測っていなかった。**

## 25. 誤検出はどこで起きているか（2026-09-13、ユーザー指摘）

「板金の曲げ構造の光の反射を誤認識しているのでは」という指摘の検証。
`tools/check_fp.py` を作って、検出を 1 個ずつ分類した（v1 の重み、閾値 0.30、val）。

### 25.1 実測 — **指摘のとおりだった**

| 材質 | 検出/枚 | 正解 | 断片 | **本当の誤検出** | うち構造の上 | うち板の外 |
|---|---|---|---|---|---|---|
| 板金 | 10.7 | 8.7% | 15.2% | **76.1%（8.2/枚）** | **52%** | 24% |
| ガラス | 13.8 | 11.8% | 27.6% | 60.6%（8.3/枚） | 0%（凹凸が無い） | 12% |
| 吸音材 | 5.0 | 0% | 5.0% | 95.0%（4.7/枚） | 35% | 56% |

- 「断片」= 正解の箱と重なるが照合が通らない（**まとめ方の問題**であって誤検出ではない）
- 板金の**本当の誤検出の 52% が板の構造の上**（曲げ・ビード・畝）に乗っている
- 図（`out/explain/fp_classes.png`）では、赤い箱が**鏡面反射した畝の上に並ぶ**

### 25.2 【訂正】「畝には反応していない」は誤りだった

§ 前回の説明で「白飛びした畝には一切反応していない」と書いたが、
**1 枚の図で目立つ筋についてだけ正しく、全体では構造が最大の誤検出源**だった。

### 25.3 誤検出は最終結果に効く

投影（第3段）に渡すものを変えて測った（val、板金＋ガラス）。

| 投影に渡した入力 | 最終Bboxの被覆 |
|---|---|
| 全検出（誤検出込み） | 16.5% |
| 正解のみ（理想） | **24.2%** |

**誤検出は速度だけの問題ではない。**変換の推定を引っ張る。

### 25.4 対策（採用）: 構造の上の負例を重くする

高さマップは**学習時には無料で手に入る**（推論では使わない）。
これまで重みは「部品表面 8.0 / 背景 1.0」の 2 段だったので、
平坦な面も畝も同じ重みだった。3 段にする。

    背景 1.0  <  部品表面 8.0  <  **構造 24.0**（STRUCT_NEG_W）

構造 = 高さの 3mm ハイパスの**上位 15%** ∪ フリット（ガラスのみ）− 刻印の膨張域。
実測で板の 10〜14%、画面の 0.7〜5.2% が該当する。

実装中に踏んだ 2 件:
- **固定しきい値 0.04mm は使えない。**面全体が細かく起伏する吸音材では
  板の 85% が「構造」になり、階層が意味を失う（板金 55% / 吸音材 85%）→ 分位で決める
- **frit 面の中身は材質で違う。**ガラスは黒フリットの疎な二値だが、
  吸音材と布タグは**アルベド地図**を載せている。素通しで OR を取ると面のほぼ全域が
  構造になった → 疎（`>0.3` が 25% 未満）のときだけ使う

### 25.5 不採用: 飽和による推論時のふるい

「白飛びした所は情報が無いので落とす」案を実測で否定。
**TP の飽和率 中央 0.06 に対し FP は 0.00** で、分離しない（むしろ TP の方が高い）。

### 25.6 保留: 必要条件によるふるい

検出の中身を見て落とす案（`docs/06_` §12-13 のエッジ密度と同じ発想）。

| 条件 | TP 残存 | FP 排除 | FP/枚 |
|---|---|---|---|
| 素通し | 100% | 0% | 7.9 |
| **エッジ塊 >= 4** | **100%** | **43%** | 4.5 |
| 面積 >= 300px² | 100% | 71% | 2.3 |
| 面積 >= 500px² | 91.8% | 80% | 1.6 |

**面積の条件は採らない。**この標本で TP を 1 つも落とさないのは、
**いまの網が小さいマークをそもそも検出できていない**から。正解の 10.6% は
長辺 30px 未満（＝ AABB で 130px² 程度）なので、300px² で切ると本来落としてはいけない
マークを落とす。**学習が進んだ後にもう一度測る。**

### 25.7 進め方

**変更は 1 つずつ。**§18 で「3 つ同時に入れて学習が壊れた」を踏んでいる。
次の学習は STRUCT_NEG_W の有無だけを振った 2 本立てにする。

## 26. 二値化で何を捨てているか（2026-09-13、ユーザー指摘）

「確率マップを二値化するのは精度上問題があるのでは。刻印部と疑陽性部で
**有意な確率差があるか**を調べよ」という指示。`tools/prob_sep.py` で測った
（v1 の重み、val 30 コマ）。

### 26.1 差は**ある**

画素ごとの確率:

| 領域 | 中央 | 90分位 | 刻印との AUC |
|---|---|---|---|
| **刻印** | **0.299** | 0.636 | — |
| 部品表面（非刻印） | 0.093 | 0.175 | **0.920** |
| 構造の上 | 0.111 | 0.183 | **0.902** |
| 背景 | 0.070 | 0.134 | 0.965 |

塊（低い閾値 0.15 で拾ったもの）の統計量で正解と誤検出を分けると:

| 統計量 | 正解 中央 | 誤検出 中央 | **AUC** |
|---|---|---|---|
| **平均 x log面積** | 2.397 | 0.448 | **0.989** |
| 平均確率 | 0.334 | 0.139 | 0.987 |
| 90分位 | 0.638 | 0.162 | 0.982 |
| 面積 | 2033 | 26 | 0.972 |

**ほぼ完全に分かれる。**平均確率 0.19 で切ると、正解の 92.3% を残して
誤検出の 98.9% を落とせる。**現行はこの順位情報を丸ごと捨てている**
（閾値を超えた塊を全部そのまま採用している）。

### 26.2 ただし「閾値を下げて順位で拾う」は**効かなかった**

同じ網の出力に、まとめ方を 4 通り掛けて比べた（`tools/group_ab.py`、val 57 コマ）。

| 方式 | R | 誤検出/枚 | 2個以上 |
|---|---|---|---|
| **現行 閾値0.30 + 連結成分** | **26.6%** | 6.9 | 31.6% |
| 低閾値0.15 + 平均確率で足切り | 7.1% | 0.7 | 10.5% |
| ヒステリシス（種0.45 / 育て0.12） | 2.0% | 1.0 | 1.8% |
| 分水嶺 + 足切り | 22.2% | 10.0 | **35.1%** |

**閾値を下げると隣のマークが融合する。**順位は「与えられた塊」しか並べ替えられない
ので、塊そのものが壊れていては効かない。分水嶺の種の高さも振ったが
（0.30/0.40/0.50 x 足切り 3 段）、現行を上回らなかった。

**結論: 情報はあるが、いまの「閾値 → 連結成分」という構造では取り出せない。**
取り出すには、連結性でなく**インスタンスを直接分ける**表現が要る
（中心度・オフセット場、または §27 の塊の枝）。**緩和された 150ms はここに使う。**

### 26.3 いますぐ効く一手: 現行の塊に順位で足切り

塊の作り方は変えず、**採否だけ順位で決める**なら今日から効く。

| 足切り | R | 誤検出/枚 | 2個以上 |
|---|---|---|---|
| 素通し（現行） | 32.8% | 8.6 | 43.4% |
| 平均 x log面積 >= 2.1 | 31.9% | **2.5** | 41.5% |
| 平均 x log面積 >= 2.7 | 29.0% | **1.5** | 39.6% |
| 平均確率 >= 0.40 | 26.5% | 1.7 | 37.7% |

**誤検出が 8.6 → 2.5 に減って R は 0.9 ポイントしか落ちない。**
§25.3 で「誤検出は最終 Bbox の被覆を 24.2% → 16.5% に下げる」と測っているので、
これは実質的な改善になる。**ただし採用は学習後**（v1 は弱いので、
新しい重みで測り直してから既定にする）。

## 27. 速度要件の変更（指示 2026-09-13）

**100ms 一括 → 確率マップまで 50ms / 最終 Bbox まで 150ms。**

| 段 | 予算 | 現状の見積り |

## 28. 【重要】検出率の 60 ポイントは**まとめ方**で失っている（2026-09-13）

ユーザー提案:「確率が明らかに低いものだけ落として、**残りのマップの位置関係を
エンコードして** Bbox を生成させる。決定論に頼らない」。

その前に、**その方向にどれだけ伸びしろがあるか**を測った（v1 の重み、val 58 コマ）。

### 28.1 生き残る点は十分にある

| 閾値 | 1枚あたりの残存点 | 正解マークの箱の中に**4点以上**残る割合 |
|---|---|---|
| p>0.05 | 44,094 / 49,152 | 100.0% |
| **p>0.10** | 15,161 | **99.2%**（箱の中に中央 408 点） |
| p>0.15 | 6,003 | 96.6% |

**ほぼ全部のマークについて、信号は残っている。**

### 28.2 上限の実測 — **93.3%**

生き残った点を「正しいマークへ割り当てられたら」どうなるかを測った
（正解の箱で割り当てる＝理想の第2段）。

| | R | 誤検出/枚 |
|---|---|---|
| 現行（閾値0.30 → 膨張 → 連結成分） | **32.8%** | 7.84 |
| **理想の割り当て（p>0.10 の点を割り当て）** | **93.3%** | 0.24 |

**いまの網のままで、まとめ方だけで 32.8% → 93.3% の余地がある。**
検出率が低いのは網が見えていないからではなく、**連結成分がマークを
切り分けられないから**だった。

**閾値の高さも効く。**p>0.30 で割り当てると 68.1% までしか行かない
（マークの端が落ちて箱が縮む）。**低く拾って後で分ける**のが正しい。

### 28.3 第2段の設計（案）【**§29 で差し替え**。閾値は不要だった】

```
① CNN -> 確率マップ            stride 2、29ms（50ms 枠内）
② 疎なトークン化               p>0.10 を stride 8 へ max-pool、上位 K=512 点
   トークン = (x, y, 平均p, 最大p, 局所の 2 次モーメント, 特徴 16〜32 次元)
③ 位置関係のエンコード          自己注意 4 層 d=96（**0.2 GMAC。無視できる**）
④ 出力                         トークンごとに「所属マークの中心へのオフセット」
                               + 寸法 + 向き。**投票の集まり**でインスタンスを分ける
⑤ 箱                           同じインスタンスに属する stride 2 の画素から OBB
```

- **連結性を使わない。**隣接する 2 行が繋がっていても、投票先が違えば分かれる
- **教師は無料。**正解ホモグラフィから「どの画素がどのマークか」が厳密に分かる
- **計算量は問題にならない。**N=512 の注意 4 層で 0.2 GMAC（本体は 29.7 GMAC）。
  緩和された 150ms 枠には十分収まる

| 学習が難しい（DETR 系は収束が遅い） | **オフセット投票**を主にする（CenterNet 系。O(N) で収束が速い）。注意は精緻化に使う |

## 29. 【差し替え】閾値は要らない — 確率を**重み**として使う（2026-09-13）

§28.3 では「p>0.10 で落としてから疎なトークンにする」と書いたが、
ユーザーの指摘:「決定論を排すという趣向なら、**落とさずに渡すべき**では」。

測り直した（v1 の重み、val 58 コマ。割り当ては理想＝正解の箱で行い、
**箱の作り方だけ**を変える）。

| 箱の作り方 | R |
|---|---|
| 現行（閾値0.30 → 膨張 → 連結成分） | 32.8% |
| 理想割当 + 二値 p>0.10 | 93.3% |
| 理想割当 + 二値 p>0.05 | 94.5% |
| 理想割当 + 二値 p>0.02 | 94.5% |
| **理想割当 + 確率で重み付けした 1次/2次モーメント（閾値なし）** | **97.1%** |

**指摘のとおりだった。**閾値は低くすれば差が消え（0.05 と 0.02 が同じ）、
**そもそも掛けずに確率を重みとして使う方が上**（94.5% → 97.1%）。
二値化は「どの画素を数に入れるか」を 0/1 で決めるので、
**縁の弱い画素の寄与が階段状に切り替わる**。重みなら連続に効く。

OBB は重み付きモーメントから作れる。

    中心   = Σ p·x / Σ p
    共分散 = Σ p·(x-μ)(x-μ)^T / Σ p   -> 固有ベクトルが長辺の向き、固有値が広がり

### 29.1 差し替え後の設計

```
① CNN -> 確率マップ p と特徴      stride 2、29ms（50ms 枠内）
② 密なオフセット頭               画素ごとに「所属マークの中心へのベクトル」を回帰
                                  **閾値なし。全画素が対象**
③ 重み付きハフ投票                各画素の投票を重み p で集積（p=0.01 の画素は 1% 効く）
                                  -> 集積マップの山が インスタンス
④ 柔らかい割り当て                画素を山へ（投票先の距離で）柔らかく配る
⑤ 箱                             インスタンスごとに**確率で重み付けしたモーメント**で OBB
⑥ 山どうしの関係を注意で符号化     山は高々 32 個。間隔・共線性・寸法の一貫性を見て
                                  スコアを付け直す（**ここが「位置関係のエンコード」**）
```

**決定論的な切り分けはどこにも無い。**唯一の離散化は「山を数える」ところで、
それも上位 k 個を候補として残し、採否は第3段（投影）と古典側に委ねる。

### 29.2 なぜ注意を「画素」でなく「山」に掛けるか

§28.3 では p>0.10 の点を 512 個に間引いてトークンにする案だったが、

- 間引き自体が決定論的な捨て方になる（指摘の趣旨に反する）
- N=512 の注意より、**N≤32 の注意の方が桁違いに安く、学習も安定する**
- 山は既に「マーク候補」なので、その間の関係（等間隔・同じ向き・似た大きさ）は
  **まさに刻印の配置そのもの**。画素どうしの関係より情報が濃い

### 29.3 費用

| 追加 | 概算 |
|---|---|
| 密なオフセット頭（拡張畳み込み 2 層 + 1x1、48ch） | 約 1.5 GMAC（本体 29.7 の 5%） |
| ハフ投票（画素ごとに 1 回加算） | 約 20 万回。無視できる |
| 山の注意（N=32, d=96, 4 層） | 0.001 GMAC 未満 |

**150ms 枠に対して余裕がある。**

### 29.4 リスクの整理（更新）

ユーザー確認: **「文字は問題ない。このタスクの目的は画像の適切なクリッピングで、
文字の認識は別タスク」**（2026-09-13）。したがって §28.4 で挙げた
「トークンに字形を入れない」という制約は**外す**。

残るリスクは 1 つだけ:

| リスク | 対処 |
|---|---|
| 注意が**レイアウト**を記憶する（新品番で崩れる） | §19 と同じ hold-out を**レイアウトで**行う。第2段に拒否権を与えない |

第1段の受容野 25px の制約は**維持する**（`docs/06_` §19）。
第2段は画像を見ず、確率マップと特徴だけを見る。

### 29.5 97% は手法の限界ではなく、**私の理想割当の作り方**の限界だった

「97% を 99% にするには」という問いを受けて、残り 2.9%（7 個）の失敗を分解した。

| 重み | R | 失敗の内訳 |
|---|---|---|
| p^0.5, k=2.0 | 96.6% | 角度 8 |
| **p^1.0, k=2.0** | **97.1%** | **角度 7** |
| p^2.0, k=2.0 | 96.6% | 角度 8 |
| p^4.0, k=2.0 | 96.2% | 角度 9 |

**失敗は全部「角度」。**中心も寸法も一度も外していない。

原因は測り方だった。理想割当で画素を選ぶとき、**正解 OBB の軸平行外接**を窓に
していたので、回転した細長いマークでは**隣や背景の画素が四隅から混ざる**。
混ざった画素が共分散の主軸を回す。

窓を**正解 OBB そのもの**（回転した窓）に変えると:

| | R | 失敗 |
|---|---|---|
| p^1.0, k=1.73, **AABB 窓** | 97.1% | 角度 7 |
| p^1.0, k=1.73, **OBB 窓** | **100.0%** | **0** |

**箱の作り方（重み付きモーメント）に限界は無かった。**
残っていたのは割り当ての緩さで、そこは第2段が解く問題そのもの。

### 29.6 ここから言えること

- **重みの形は効かない。**p^0.5〜p^4 で 1 ポイント以内、k も 1.5〜2.0 で同じ。
  **softmax のような尖らせ方は不要**（むしろ p^4 が最下位）。素の p を線形に使う
- **効くのは割り当ての精度**、特に細長いマーク。角度は少数の混入画素で回る
- したがって第2段の設計目標は「**インスタンスに密着した割り当て**」であって、
  窓で切ることではない。**オフセット投票**はまさにそれ（窓を持たない）

**注意**: 100% は理想割当での上限であって、実際の第2段はこれを下回る。
この実験が示すのは「**箱の作り方は律速ではない**」ということだけ。

## 36. 【重要】合格率で測り直すと、どの方式も gen で 0〜7%（2026-09-13、Fable の助言を検証）

| **刻印パッチの縁が黒い線で写る**（ユーザー指摘） | 刻印入りの別メッシュを面から 0.02mm 浮かせていた | **STEP の B-rep に直接刻印**（下記） | 縁の勾配 / 外側の勾配: 1.68（最大 7.79）→ **0.96（最大 1.17）** |

**【撤回】`check_patch_seam.py` の「継ぎ目は見えていない（1.06）」は誤り。**ISP 後（ノイズ込み）の
8bit で勾配を測っていたため、ノイズの勾配に埋もれた。リニア EXR で測ると 1.68 倍。

### 37.4 B-rep への直接刻印（`prep_part.engrave_part`）

Blender 本体は STEP を読めないが、gmsh（OpenCASCADE）で B-rep のまま扱える。

1. B-rep を剛体変換（回転 + 平行移動）して刻印面を z=0 に。平面は平面のまま、辺の共有も保たれる
2. gmsh の Box 場で、**刻印の正方形の中だけ高さマップの画素ピッチ（約 27µm）**、外へ 6mm かけて 1.2mm まで粗く。
   部品全体が 1 枚の適合メッシュ
3. 正方形の中の節点を高さマップで z 方向へ（画素の約束は `ds.grid_to_img` と同じ）

| 項目 | 値（p9100） |
|---|---|
| 三角形 | 147 万 |
| メッシュ作成 | 36 秒（CPU） |
| 刻印の正方形内の開いた辺 | **0** |
| 刻印面の高さ | 高さマップと一致（0〜0.125mm） |
| レンダ時間 | パッチ方式とほぼ同じ |

## 38. 合格条件（面積 150% 上限）の影響と、吸音材の撮影条件の緩和（2026-09-14、指示）

### 38.1 面積上限 150% はどれだけ効いているか（学習済み A をそのまま、全コマ）

同じ予測を、合格条件だけ変えて数え直した（`viz_block2.py --dump` → コマごとの s* と面積比）。

| gen | 上限 1.5: 合格 | 覆えず | 覆えたが面積超過 | 上限 2.0: 合格 | 面積超過 |
|---|---|---|---|---|---|
| ガラス（504） | 93.3 | 2.2 | 4.6 | **97.2** | 0.6 |
| 布タグ（378） | 94.7 | 1.9 | 3.4 | **98.1** | 0.0 |
| 実部品（661） | 64.8 | 14.4 | **20.9** | **79.7** | 5.9 |
| 吸音材（376） | 7.2 | 31.1 | 61.7 | 27.4 | 41.5 |
| **吸音材以外（1,543）** | **81.4** | 7.3 | **11.3** | **90.0** | 2.7 |
| 全体（1,919） | 66.9 | 12.0 | 21.2 | 77.7 | 10.3 |

- **影響している。**吸音材以外の不合格 18.6pt のうち **11.3pt が「覆えているのに面積が 1.5 倍を超えた」**
- 超過はほとんど**わずか**: 覆えたコマの面積比 中央 1.34 / 90 分位 1.55 / 95 分位 1.71 / 99 分位 2.79
- **中央 1.34 は損失の面積目標 A=1.3 そのもの。**網は目標にぴったり寄せており、上限 1.5 までの余裕が狭い
- 覆えないコマも**わずかに足りないだけ**: 必要倍率 中央 1.06 / 75 分位 1.13 / 90 分位 1.29
- 箱を一律に k 倍（val で k を決め gen で報告）: 上限 2.0 なら **k=1.06 で吸音材以外 92.5%**（実部品 84.7%）。上限 1.5 では k=1.00 が最良（広げると面積で落ちる）

### 38.2 吸音材の撮影条件（指示）

| 項目 | 他の材質 | 吸音材 |
|---|---|---|
| 刻印部の法線となす角 | 45 度以内（0/11/22/33/44） | **20 度以内（0/7/14/20）** |
| 教師 Bbox が画面に占める割合（幅・高さの大きい方） | 20〜70% | **70〜90%（0.72/0.80/0.88）** |

実装: `make_dataset.CASE_VIEW`。読める視点の事前計算（`prep_scene --tilts`）もレンダと同じ傾きで行う
（旧 0/11/22/33/44 のままだと、新しい傾きの視点がほぼ全部「読めない」扱いで落ちる）。`verify_dataset` の A6 も材質別の範囲に。

**画角の測り方も直した。**`block_frac`（マーク矩形の 4 隅を投影）で 0.70〜0.88 に合わせると、
回転・傾きで角が張り出すぶん、**教師 Bbox では 0.64〜0.88**（f9500、70% 未満あり）だった。
吸音材は `--frac-def ink`（刻まれた画素の輪郭を投影、`ds.block_aabb` と同じ定義）で合わせる → **0.71〜0.88、傾き最大 20 度**。

**画像での確認（f9500、1:1 切り出し）: 条件を緩めても刻印はほとんど見えない。**繊維の模様が支配的で、
くぼみによる平滑化がかすかに分かる程度。撮影条件だけでは足りない可能性が高い（合成の刻印の強さ自体の検討が要る）。

### 38.3 決定（ユーザー、2026-09-14）

**案 2 を採用: 損失の面積目標は 150%、評価は 100〜200%。**（案 1「損失も評価も 200%」は採らない）

理由（§38.1 の実測から）: 網は損失の面積目標にぴったり寄せる（目標 1.3 → 面積中央 1.34）。目標を 2.0 に上げると
箱も大きくなり、2.0 のすぐ外で同じ「わずかな超過」が起きる。目標 1.5 のまま評価を 2.0 にすれば、
上限までの 1.5〜2.0 が裾の余裕になり、目標を 1.3→1.5 に広げたぶん覆えないコマ（必要倍率 中央 1.06）も覆いやすくなる。

実装: `train_block2.py` の `A_TGT=1.5`、`AREA_MAX=2.0`、旧条件 `AREA_REF=1.5` での合格率も併記。

## 39. 実部品の「わずかな覆い漏れ」はどこで生まれるか（2026-09-14、ユーザーの仮説を検証）

**仮説（ユーザー）**: 1 段目の確率に非線形な演算（sigmoid・積）があり、弱い刻印ほど潰れて、ブロックの端を取りこぼす。
**道具**: `tools/analyze_stage1.py`（v4A、実部品 gen+val 1,025 コマ、うち覆えず 108 = 10.5%）。画像は `out/v4/stage1/`。

| # | 問い | 結果 |
|---|---|---|
| A | どの段で漏れるか | 漏れた 119 辺のうち **70% は基準箱の段で漏れ、差分頭・Refiner でも取り返せていない**。**29% は粗い箱で覆えていたのに Refiner が内側へ詰めて漏れた**。漏れ量（辺長比）: 基準 11.5% → 粗 2.3% → 最終 3.2%（中央） |
| B | 端のマークは弱いか | 漏れた辺を決めるマークは同じコマの中央値比 **p 0.91 / conf 0.94 / w 0.87**（覆えた辺は 1.00）。絶対値 p 0.34 / conf 0.82（覆えた辺 0.45 / 0.96）。**積で差は開くがわずか**（コマ内の最弱/最強 p 0.93 → w 0.91） |
| C | 重みの非線形を弱めたら基準箱は良くなるか | **良くならない。**覆うのに必要な面積（中央/90 分位）: p×conf 1.14/1.33 が最良、sqrt(p×conf) 1.16/1.39、conf 1.17/1.39、p 1.23/1.81 |
| E1 | 差分頭は w を見て辺を動かしているか | **ほぼ見ていない。**端のマークの w を 2 倍にしても差分頭経由で辺は 0.02% しか動かない（基準箱の算術経由では 3.5%）。差分頭は特徴 f で補正している |
| E2 | p は潰れているか | マーク上の logit 中央 −0.19（p=0.45）、logit>0 のマークは 15%。**p は全体に控えめ**（focal γ=2 + 部品表面の負例 8〜24 倍）。漏れた辺のマーク −0.61（p=0.35）。p<0.1 のセルは中央 2% で、**ゼロ付近に潰れているわけではない** |
| E3 | Refiner の癖 | 全体に**内側へ詰める**（中央 −1.7%、10 分位 −7.3%）。取り返した辺 48、壊した辺 36 |
| E4 | conf（塊の一部か）の広がり | **最も分かれる量。**conf が 0.5 を切る位置は、覆えた辺では正解の辺の 3.7% **外側**、漏れた辺では 5.6% **内側**（90 分位 17.5%） |
| F | 学習し直さずに組み立てだけ変えたら | 最終 80.8% / Refiner なし 73.2% / Refiner は外へだけ 77.4% / 一律 1.04 倍 **81.7%**（最大でも +0.9pt）。**覆えない箱と大きすぎる箱が別々に存在し、一律の補正では両方は直らない** |

### 結論

- **仮説は半分当たり。**漏れた辺の端のマークは 1 段目で弱く、積で差もわずかに開く。しかし**非線形を弱めても基準箱は良くならず**（C）、
  差分頭は w の値をほとんど使っていない（E1）ので、**w の演算を変えるだけでは辺は動かない**
- **決め手は「塊の広がり」を表す conf が、弱い端のマークで正解の辺より内側で途切れること**（E4）。
  1 段目は「マーク（筆画）の証拠」は出しているが、「ブロックがどこまで続くか」を直接は表していない
- 後段は、70% をそのまま引き継ぎ、Refiner がさらに 29% を作っている
- 一律の拡大・Refiner の制限では +1pt 未満。**1 コマごとの外形の推定そのものを良くする必要がある**

## 40. 外形を 1 段目に学習させる + Refiner の詰めすぎ対策（承認 2026-09-14）

§39 の結論（覆い漏れの 70% は基準箱の段、29% は Refiner の内詰め。conf は弱い端のマークで正解の辺の内側で途切れる）への対策。
`train_block2.py --extent 1 --inward 3`。

| 部品 | 旧 | 新 |
|---|---|---|
| 1 段目の出力 | p（筆画）、conf（塊、教師はマーク単位の矩形） | **+ ExtentHead**: blk（**教師 Bbox 全体**の内側か）と、**4 辺までの符号付き距離**（全セルで学習）。拡張畳み込み d=2,4,8,16 |
| 基準箱 | w = p×conf の重み付き平均・分散（半幅 2σ、勾配は切る） | **各セルが指す 4 辺を blk で重み付き平均**（閾値なし）。勾配は外形の頭まで流れ、基準箱にも合格損失（×0.5） |
| 差分頭の入力 | f + w + 座標 | f + **blk** + 座標 |
| Refiner の入力 | 画像の切り出し（2 面） | 画像 + **p・conf・blk の切り出し**（5 面）。かすかな端のマークを「何も無い」と見て詰めないように |
| Refiner の損失 | 合格損失のみ | + **内詰めの罰**: 粗い箱で覆えていた辺を最終で漏らしたら、その漏れ（正解の辺長比）× 3 |

## 42. 実物の知見を反映: 吸音材の焼き印・最新カメラのノイズ・1024px 入力（2026-09-14、ユーザーの見解）
